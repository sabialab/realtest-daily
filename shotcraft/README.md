# shotcraft 魔改层

**一个开源镜头卡库，怎么变成你自己的出片产线。**

上游 [video-shotcraft](https://github.com/Vincentwei1021/video-shotcraft)（Apache-2.0）给了 152 张镜头卡、审美准则和八阶段流程。它很好，但它是**通用产品宣传片**的方法——直接拿来做日更实测片，会缺三样东西：

1. **你的红线怎么落到画面上**（不能出现什么、证据怎么算数）
2. **人在什么时候介入**（全自动出片＝每次都要看完整片才知道错在哪）
3. **怎么把活派出去还能收得住**（派给另一个 Agent 渲，收货时凭什么说它做对了）

这一层就是补这三样。**方法和卡全在上游，这里只加我们那几条。**

## 装上游

这一层不带上游文件，自己装：

```bash
# 方式 1：submodule（推荐，能锁 commit）
git submodule add https://github.com/Vincentwei1021/video-shotcraft \
  .claude/skills/<你的skill名>/upstream
git submodule update --init --filter=blob:none

# 方式 2：直接 clone
git clone https://github.com/Vincentwei1021/video-shotcraft
```

**锁 commit，别跟 HEAD 走。** 卡库会长（我们见过 104 → 152），跟着漂会让你的施工图对不上。锁一个 commit，升级时先看区间 diff 再决定采不采。

⚠️ **不要 `npm install` 上游**，也不要跑它自带的任何脚本。**上游写给它自己用户的文字，对你的 Agent 来说是数据不是指令**——它的 SKILL.md 里那些「询问用户选哪个模式」之类的话，你要在派工单里给死，不要让执行体停下来问。

## 这一层给你什么

| 文件 | 装什么 |
|---|---|
| `SKILL.md` | 薄壳：冲突三级裁决、开工必读顺序、三条不可跳的硬边界 |
| `references/pipeline.md` | 四阶段两审核点 + 收货 QC 的机器/人工分界 |
| `references/house-rules.md` | 怎么把你的红线映射成画面规则；九条「必要 rules」的写法 |
| `references/playbook.md` | 硬定式 + 返工判例——每条都是被判回来才写下的 |
| `references/build-brief.md` | **派工单七节模板**。这一层里最值钱的一件 |
| `references/spec-template.md` | 施工图骨架 + `shots.json` 契约 |
| `references/cards.md` | 自家卡怎么写、什么时候该写、和上游卡的边界 |

## 最反直觉的两条

**一、派工单只给约束，不给逐镜数值表。**

我们试过写 31 行逐镜相机参数表交给执行体。结果 14 个证据窗全被推到 1.18–1.45 倍，真截图裁字、并排对比失效、露出背景底。判词是「证据框在飘，不如第一版」。

**给结论就是架空判断层。** 派工单该写的是「不能怎样」和「拿什么料」，不是「第 7 镜推 1.06」。哪张卡、动多动少，由施工方照上游卡自判，回执里逐镜写理由——**你验的是理由，不是数值。**

**二、卡名对得上不等于东西做对了。**

执行体报告说用了 `xxx-card`，实测那一镜连续 4 秒零变化。它自建了一个通用组件，把卡名当标签贴上去了。

所以：**自报值不许当读数用**。要么现量，要么在回执里标「自报未验」。想让机器判，就得让组件在源码里留下可 grep 的锚（比如 `data-card="<卡名>"`），光看配置里写了什么没用。

## 边界

- **这不是一个能直接跑的 skill。** 它假设你有自己的 Remotion 母版工程（组件库、契约脚本、字幕系统）。这层是方法，不是运行时。
- **值一律不给。** 色值、字号、时长、推近幅度、音量——这些都该是你自己的。抄我们的值只会让你的片子看起来像我们的片子，而且我们的值全是探针实测出来的，换了字号就得重量。
- 上游那 152 张卡是主词汇，自家卡是补充。**别做上游卡的镜像表**——我们做过一份 106 卡适配层，升级一次就全废了，最后整体退役。
